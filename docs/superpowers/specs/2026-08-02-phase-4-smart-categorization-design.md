# Phase 4 Smart Categorization Design

Date: 2026-08-02
Status: Approved design
Branch: `codex/phase-4-smart-categorization`

## Goal

Categorize newly created transactions without delaying creation. The system
uses deterministic user rules first and OpenAI only as a fallback. Users can
always override automation and may explicitly turn a correction into a new
rule.

The final priority is:

1. manual category selection;
2. matching user rule;
3. OpenAI fallback;
4. uncategorized.

## Scope

Phase 4 includes:

- per-user keyword-to-category rules with CRUD and RLS;
- background categorization for transactions created without a category;
- case-insensitive substring rule matching;
- OpenAI fallback constrained to categories visible to the signed-in user;
- categorization source and status on transaction responses;
- an Auto badge, progress and failure states, retry, and a Rules page;
- an explicit “Save this as a rule” flow after a manual correction;
- backend, PostgreSQL/RLS, OpenAI-adapter, and frontend tests.

Phase 4 does not include:

- automatically learning rules without confirmation;
- regex, amount, account, or date-based rule conditions;
- a separate queue such as Celery or Redis;
- bulk historical recategorization;
- sending amounts, account data, user identifiers, or access tokens to
  OpenAI;
- using OpenAI when a deterministic rule already matched.

## Transaction Lifecycle

### Manual category selected at creation

FastAPI validates the selected category, saves the transaction with
`category_source = 'manual'` and `categorization_status = 'categorized'`, and
does not schedule automatic categorization.

### Auto categorize selected at creation

FastAPI saves the transaction immediately with no category,
`category_source = null`, and `categorization_status = 'pending'`. After the
response is ready, a FastAPI background task categorizes the transaction.

The task reloads the transaction and stops unless all of these remain true:

- it belongs to the initiating user;
- its status is still `pending`;
- it has no category;
- it has not been manually edited since the task was scheduled.

It then tries the enabled rule engine. If no rule matches, it calls the OpenAI
adapter. Before writing either result, it performs the same guard in the
database update so a concurrent manual choice cannot be overwritten.

### Manual correction

Any category selected through transaction update becomes authoritative:
`category_source = 'manual'`, status becomes `categorized`, and
`categorized_at` is updated. A pending background result cannot replace it.

When an automatic category is corrected, the frontend offers “Save this as a
rule.” Saving the category does not depend on accepting that offer. The rule
form suggests an editable keyword derived from the description, and the user
must confirm it explicitly.

### Failure and retry

Missing configuration, timeouts, refusals, invalid structured output, provider
errors, or no suitable category leave the transaction intact. Provider errors
set `categorization_status = 'failed'`; a valid response with no meaningful
category sets `not_requested`. Both remain visibly uncategorized. The retry
endpoint atomically moves an eligible non-pending transaction to `pending` and
schedules a new task. An already-pending or manually categorized transaction
returns `409`, so concurrent duplicate requests enqueue at most one task.

## Data Model

### `categorization_rules`

| Column | Type | Rules |
| --- | --- | --- |
| `id` | `uuid` | primary key, generated by PostgreSQL |
| `user_id` | `uuid` | required, references `auth.users(id)` |
| `keyword` | `text` | trimmed, 1–120 characters |
| `category_id` | `uuid` | required, references `categories(id)` with `ON DELETE CASCADE` |
| `enabled` | `boolean` | required, defaults true |
| `created_at` | `timestamptz` | required, defaults now |
| `updated_at` | `timestamptz` | required, defaults now |

Keywords are case-insensitively unique per user. RLS is enabled and forced;
users can only read and mutate their own rules. A database trigger rejects a
rule whose category is neither global nor owned by the same user.

The list query is deterministic. Matching normalizes the description and
keyword with case-folding, checks substring containment, and selects the
longest matching keyword. Equal-length matches are ordered by normalized
keyword and then rule ID.

### Transaction additions

| Column | Type | Rules |
| --- | --- | --- |
| `category_source` | `text` | null or `manual`, `rule`, `openai` |
| `categorization_status` | `text` | `not_requested`, `pending`, `categorized`, `failed` |
| `categorized_at` | `timestamptz` | nullable |

The migration backfills existing transactions with a category as `manual` and
`categorized`. Existing transactions without a category become
`not_requested`. The migration is additive and idempotent.

No OpenAI prompt, response body, confidence score, or provider identifier is
stored. The source is sufficient for the product UI and avoids retaining
unnecessary model output.

## Backend Boundaries

### Rule repository and service

The rule repository owns authenticated CRUD, deterministic list order, and the
guarded lookup of matching rules. The rule service validates ownership and
maps repository errors to stable HTTP responses.

### Categorization service

The service coordinates one attempt:

1. reload and guard the transaction;
2. load enabled rules and visible categories;
3. apply the deterministic matcher;
4. call the configured provider only when no rule matched;
5. perform a guarded transaction update;
6. mark provider failures without changing the category.

The service depends on a provider protocol rather than the OpenAI SDK directly.
Tests use a fake provider and CI makes no external API calls.

### OpenAI adapter

The adapter uses the OpenAI Responses API with structured output. Its input is
limited to:

- normalized transaction description;
- transaction type (`income` or `expense`);
- visible category IDs and names.

The schema returns either one supplied category ID or null. The backend still
validates the returned ID against the allowed set. The prompt instructs the
model to return null when no category is meaningfully supported.

The Responses request sets `store=false`, which disables application-state
storage for that response. Ordinary OpenAI abuse-monitoring retention is
separate; this setting alone is not Zero Data Retention.

Configuration:

- `OPENAI_API_KEY` is required only for the fallback and remains server-side;
- `OPENAI_CATEGORIZATION_MODEL` defaults to `gpt-5.6-luna`;
- a short provider timeout is configurable;
- application logs record outcome and latency without raw descriptions or
  model response content.

OpenAI background mode is not required. The call runs inside the application’s
FastAPI background task because this classification is small and bounded.

## API Contract

### Rules

- `GET /categorization-rules` returns the signed-in user’s rules with category
  display data.
- `POST /categorization-rules` creates a rule.
- `PATCH /categorization-rules/{rule_id}` edits keyword, category, or enabled
  state.
- `DELETE /categorization-rules/{rule_id}` deletes a user-owned rule.

Duplicate keywords return `409`. Invalid or unavailable categories return
`422`. Unknown or another user’s rule returns `404` to avoid disclosing it.

### Transactions

Transaction output adds `category_source`, `categorization_status`, and
`categorized_at`.

`POST /transactions/{transaction_id}/categorize` retries only a user-owned,
eligible non-pending transaction. It returns `202` with the transaction in
`pending` state. An already-pending or manually categorized transaction
returns `409` rather than enqueuing duplicate work or replacing the user’s
choice.

Transaction create and update preserve the existing category/account
validation. Setting a category manually always sets the manual source and
categorized status. Clearing a category explicitly results in
`not_requested`; automation resumes only through the retry action.

## Frontend Design

### Transaction form and list

The create form category selector’s empty/default choice is labelled “Auto
categorize.” The edit form uses “Uncategorized,” because saving that choice
sets `not_requested` without scheduling background work. A named category is a
manual choice.

The list renders:

- `Categorizing…` for pending work;
- an Auto badge for `rule` and `openai` sources, with accessible text naming
  the source;
- the normal category without a badge for manual choices;
- `Uncategorized` and Retry for failed work;
- `Uncategorized` and Categorize for eligible `not_requested` work.

Polling is bounded to rows that are pending. The transactions query is
invalidated after background completion or retry, and all keys remain scoped
by authenticated user ID.

### Correction-to-rule flow

After changing a rule- or OpenAI-assigned category, the UI offers a separate
rule form. It suggests a keyword from the description, requires confirmation,
and allows edits. Dismissing it has no effect on the saved manual correction.

### Rules page

The authenticated Rules page provides create, edit, enable/disable, and delete
actions. Category choices show global and user categories by name. Global
categories remain readable but never mutable. Rule query keys include the
authenticated user ID, and mutations invalidate only that user’s rule cache.

## Concurrency and Security

- User identity always comes from the verified Supabase JWT `sub`.
- Every repository operation carries the user ID and uses the existing local
  RLS session context.
- Forced RLS protects rules and transaction updates.
- Category ownership is validated in FastAPI and by a database trigger.
- The final categorization write is conditional on the transaction still
  having no manual category selection.
- Multiple background attempts are idempotent: only the first eligible guarded
  update succeeds.
- The OpenAI API key, prompt, and provider response never reach the frontend.

## Testing

### Backend unit and API tests

- case-insensitive substring matching;
- longest-keyword and deterministic tie-breaking;
- rule CRUD, duplicates, validation, and isolation;
- manual create bypasses automation;
- rule match bypasses OpenAI;
- OpenAI fallback accepts only allowed structured category IDs;
- null result, missing key, timeout, refusal, and provider error behavior;
- retry eligibility and responses;
- concurrent manual override protection;
- source/status serialization and migration backfill assumptions.

### PostgreSQL integration tests

- forced RLS isolation for rules;
- global versus user-category ownership;
- cross-user category rejection by the trigger;
- category deletion cascading to rules while preserving transactions;
- guarded automatic update cannot overwrite a manual category;
- migration idempotence.

### Frontend tests

- create-form Auto categorize, edit-form Uncategorized, and manual selection;
- pending, rule, OpenAI, manual, not-requested Categorize, failed, and Retry states;
- correction offer and independent rule creation;
- Rules page CRUD and enable/disable behavior;
- authenticated query-key isolation;
- loading, error, and empty states.

The full backend PostgreSQL suite, Ruff, frontend tests, lint, and production
build must pass. Real-provider smoke testing uses a dedicated test transaction
and confirms that no secret appears in browser bundles or logs.

## Delivery and Rollout

The feature remains functional without `OPENAI_API_KEY`: deterministic rules
still work and unmatched transactions fail gracefully. Database migration and
rule engine can therefore deploy before enabling the OpenAI fallback.

Phase 4 is complete when:

1. rules and OpenAI fallback categorize new uncategorized transactions in the
   approved priority order;
2. manual selections and corrections cannot be overwritten;
3. rule CRUD and RLS isolation work for two users;
4. the frontend exposes source, progress, failure, retry, and rules management;
5. automated checks pass and one server-side OpenAI smoke test succeeds;
6. Phase 4 documentation records any remaining authenticated UI smoke gap
   without claiming unverified behavior.
